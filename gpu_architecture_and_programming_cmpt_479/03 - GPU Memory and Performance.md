## Performance limits and arithmetic intensity

Two useful hardware ceilings are computational throughput (operations per second) and memory bandwidth (bytes transferred per second). A kernel is often:

- **Compute-bound** when arithmetic throughput is the main limit.
- **Memory-bound** when data movement is the main limit.

Arithmetic intensity (also called computational intensity) is the number of floating-point operations per byte transferred from global memory:

\[
I = \frac{\text{FLOPs}}{\text{bytes transferred}}
\]

The relevant byte count depends on the memory traffic actually generated by the implementation.

## Roofline model

The roofline model bounds attainable performance by the lower of the compute ceiling and the bandwidth ceiling multiplied by arithmetic intensity:

\[
P \le \min(P_{\text{peak}},\; BW_{\text{peak}} \times I)
\]

The sloped bandwidth limit and horizontal compute limit meet at the “ridge point.” Below it, performance is bandwidth-limited; above it, compute throughput is the limit. For the slide’s H100 example (67 TFLOP/s and 3.35 TB/s), the ridge point is about 20 FLOP/B. Hardware figures vary with model, data type, and conditions.

For vector addition, each element performs one addition and transfers two 4-byte inputs plus one 4-byte output: 1 FLOP / 12 bytes, or about 0.083 FLOP/B. This low intensity indicates a memory-bound operation under the cited example.

## Memory hierarchy and CUDA storage

GPU storage includes registers, shared memory, caches, and device global memory. These levels differ in capacity, latency, scope, and how they are accessed. Registers are private to a thread; shared memory is explicitly managed and shared by threads in a block; global memory is broadly accessible but has higher latency.

CUDA variable declarations and allocation choices determine where values live and who can access them. Use shared memory when threads in a block reuse data, while accounting for synchronization and the limited per-SM capacity.

## Tiling matrix multiplication

In a basic matrix multiplication kernel, each output element computes a dot product and loads input values from global memory. Across the output tile, many threads reuse the same input elements, so the basic implementation can generate redundant global-memory traffic.

Tiling stages a small input tile into shared memory, lets a block reuse those values to compute several output elements, then advances through the matrices’ inner dimension. A correct tiled kernel coordinates stages with barriers: synchronize after loading before consuming the tile, and before overwriting shared storage needed by other threads.

Tiling increases reuse and arithmetic intensity, but shared-memory use can reduce the number of resident blocks and therefore occupancy. Tune tile size with both data reuse and resource limits in mind. Handle matrix dimensions that are not tile multiples with bounds checks.

## Global memory coalescing

Memory accesses from neighboring threads are most efficient when they address nearby locations that can be served by a small number of memory transactions. This is called coalescing. For row-major arrays, mapping adjacent `threadIdx.x` values to adjacent columns commonly produces contiguous accesses. Strided or scattered accesses can require more transactions and reduce effective bandwidth.

## Hiding latency and using bandwidth

The scheduler can run another ready warp while one warp waits for memory. Sufficient independent work helps hide latency. Effective bandwidth also depends on coalesced accesses, enough parallel requests, and avoiding unnecessary transfers. Occupancy is a resource constraint and a tool for latency hiding; maximizing its percentage alone does not ensure best performance.

## Analysis checklist

1. Count arithmetic operations and global-memory bytes.
2. Estimate arithmetic intensity and locate the kernel on the roofline.
3. Identify repeated data that could be reused from a faster memory level.
4. Check access patterns across neighboring threads for coalescing.
5. Consider register and shared-memory use alongside occupancy.
6. Measure on the target GPU; theoretical ceilings are guides, not performance guarantees.
